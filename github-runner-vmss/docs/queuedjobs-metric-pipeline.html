Azure Monitor · runner autoscale

How QueuedJobs becomes an autoscale signal

The GitHub queued-run count is polled by a workflow, POSTed to Azure Monitor as a custom metric on the VMSS resource, and read by the autoscale rule. It is a time series, not a log — it never touches the Log Analytics workspace.

Short answer

No — it is not a table in Log Analytics. QueuedJobs lives in Azure Monitor Metrics: a numeric time-series store attached directly to the VMSS resource, under the namespace GitHubActionsQueue. Metrics and Logs are two separate data planes.

The Log Analytics workspace in this project holds something else entirely — the runner instances’ Syslog and Perf, shipped by the Azure Monitor Agent. Autoscale never queries it.

Two data planes, one product name

“Azure Monitor” covers both, but Metrics and Logs are stored, priced, and queried separately.

In this project QueuedJobs in GitHubActionsQueue, posted by poll-queue-depth.yml Runner Syslog (bootstrap logs on facility local0) and Perf, via AMA
The one bridge that looks like it should apply, but doesn’t. A diagnostic setting can copy a resource’s platform metrics into the workspace’s AzureMetrics table. It does not pick up custom metrics you POST yourself, and autoscale reads the Metrics store directly regardless — so wiring one up would not put QueuedJobs in Log Analytics, and would not change scaling behaviour either way.

Why the split matters here

  • Staleness stops scale-out, silently. If poll-queue-depth.yml misses its window (GitHub’s schedule is best-effort), no fresh QueuedJobs point lands. The autoscale rule then has nothing above threshold to act on, so a queued job waits — there is no fallback to “check the logs”.
  • You debug scaling in two different places. Did the metric arrive? → Metrics Explorer / az monitor metrics list. Did autoscale act on it? → the scale set’s Scaling → Run history. Did the runner bootstrap? → Log Analytics Syslog. Three tools, one pipeline.
  • Wanting the count in KQL means shipping it twice. To trend QueuedJobs alongside the runner logs you would send it to a custom workspace table as a second, independent ingestion. It will never appear in Log Analytics as a side effect of the metric POST.

Checking each leg

# 1. did the metric land? (Azure Monitor Metrics)
az monitor metrics list \
  --resource "$VMSS_RESOURCE_ID" \
  --namespace GitHubActionsQueue --metric QueuedJobs \
  --query "value[].timeseries[].data[-1]"

# 2. did autoscale act? — portal: VMSS → Scaling → Run history

# 3. did the runner bootstrap? (Log Analytics — different store, KQL)
Syslog | where Facility == "local0" | order by TimeGenerated asc
